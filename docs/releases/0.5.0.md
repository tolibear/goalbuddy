# GoalBuddy 0.5.0: One Goal Router, Quiet Runtime

GoalBuddy 0.5.0 makes the local fork one coherent installed product. Codex Goal Compiler is the single goal-routing front door, with separate native-goal and focused GoalBuddy board compiler backends. Goal Prep owns the GoalBuddy schema as a non-model-invocable-by-default backend and explicit manual repair surface. During execution, the safety control plane remains fully active but routine user updates stay focused on product work.

## What changes

- `codex-goal-compiler/` and `goalbuddy/` are canonical sibling skill trees in this repository and byte-exact plugin mirrors.
- Codex and Claude installs receive both skills. The plugin composer opens Codex Goal Compiler; direct Goal Prep remains available for intentional board intake or repair.
- The compiler selects direct work, planning, standalone native goals, GoalBuddy boards, Omega, or recurring automation before loading a route-specific backend. Missing material source decisions return `not_compilable` without creating a board or inventing another workflow.
- The compiler preserves large-spec vertical slices and compiles an adaptive execution strategy so the runtime chooses upfront, just-in-time, or hybrid planning plus native plan/review/simplification capabilities at live seams.
- Routine successful resume, Ledger, Keeper, digest, receipt, checker, prompt-rendering, and polling mechanics stay out of user-facing updates. Product milestones, independent reviews, real blockers, required decisions, and completion evidence remain visible.
- Complete canonical board decisions now use digest-bound typed transitions directly: receipt closeout plus successor activation, exact task-card amendment, hydration, exact-human wait/reply, and completion. Keeper remains mandatory for full-board inspection, repair, runtime rebinding, ambiguity, and noncanonical control work. An already-known one-location scalar or one-line annotation may still use the narrow exact-context path with the current digest and an immediate checker run.
- Prompt rendering and mixed-vendor dispatch admit only the checker-validated current active task at an exact digest. Dispatch rereads immediately before launch and reconciles a content-aware write manifest with both `allowed_files` and receipt `changed_files`, including second edits to pre-dirty paths and forbidden GoalBuddy control writes.
- Strict continuation preserves valid YAML literal and folded block scalars used by existing long-running boards. Checker-accepted cards that omit the receipt field are treated as receipt-free and are canonicalized when their first typed transition records a receipt; newly compiled cards still write `receipt: null` explicitly.
- `goalbuddy contract --target codex|claude --json` exposes compiler contract v1: product and board-schema versions, named runtime capabilities, source provenance, and target readiness.
- The compiler preflight consumes only that contract. It requires its seven safety capabilities but accepts additive capabilities and fields, so ordinary GoalBuddy evolution no longer breaks on an exact version, agent count, file list, or doctor-output shape.
- Doctors fail closed when the bundled compiler or backend is missing or stale. Codex also rejects a second standalone compiler that could shadow the product-owned copy.
- An explicit local-source cutover replaces the configured GoalBuddy marketplace by name before adding the verified checkout, while the surrounding install transaction retains rollback ownership of both harnesses.
- This fork is a private local package tied to `Danielalnajjar/goalbuddy`; npm publishing machinery is removed so it cannot overwrite the upstream package.

## What does not change

- Board schema remains `version: 2`.
- Board schema, historical receipt bytes, Ledger recovery, and existing-board compatibility remain unchanged. Before activation, receipt, prompt, and dispatch authorization are tightened around one exact checker-admitted current task; no historical board migration is required.
- Existing and historical boards are not migrated or rewritten.
- The compiler's restored single-front-door interface and two-backend boundary are audited as semantic version `4.0.0` inside the GoalBuddy product release.
- Existing inherited `goal-maker` aliases remain untouched in this release. No new compatibility layer is introduced.

## Activation boundary

The candidate is built and tested in an isolated worktree and an isolated user home containing isolated Codex/Claude homes. Set `HOME`, `CODEX_HOME`, and `CLAUDE_HOME` together for a dry run: Codex also discovers shared skills below `~/.agents`, so changing only the two harness-home variables is not a complete isolation boundary. Making it live is a separate owner-approved step:

1. Land the GoalBuddy candidate only; keep the skills-repo compiler source and live links intact.
2. Point Bun's existing local GoalBuddy dependency at the landed checkout. Package installation does not mutate either harness.
3. Run `goalbuddy install`. It snapshots GoalBuddy-owned Codex and Claude surfaces, installs both targets, retires only the recognized standalone compiler symlink after the bundled copy exists, verifies both doctors, and restores the snapshot on any failure.
4. Run both compiler contracts and both doctors from a fresh process.
5. Verify representative current boards are byte-identical and still resume/prompt correctly.
6. Only after those proofs pass, land the skills-repo ownership-transfer commit that deletes the former compiler source.

If activation fails, require the transaction report to say `rolled_back` before continuing on 0.4.0. A `rollback_failed` report is a hard stop and preserves its recovery snapshot path. Never land the skills transfer, introduce a runtime shim, or rewrite board history to recover.
